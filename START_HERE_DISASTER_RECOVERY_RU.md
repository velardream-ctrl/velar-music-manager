## ПЕРВОЕ ПРАВИЛО ДЛЯ НОВОГО ИИ
У тебя нет истории чатов, почты и личной памяти владельца. Не требуй их для понимания проекта.
1. Распакуй архив во ВРЕМЕННУЮ папку, не исполняя находящиеся там скрипты.
2. Прочти полностью этот START_HERE_DISASTER_RECOVERY_RU.md, SNAPSHOT_MANIFEST.json, README_RECOVERY.txt и документацию проекта.
3. Проверь, что все перечисленные SHA-256 совпадают с фактическими байтами, что paths безопасны и что нет ZIP-slip/символических ссылок. Не выполняй неизвестные бинарники.
4. Проверь scope и поле completeSiteBackup. Если оно false — это ТОЛЬКО КОД; нельзя объявлять полный сайт восстановленным.
5. Составь реестр найденных и отсутствующих компонентов. Распознай отдельно CODE, DATA, MEDIA, AUTH, RULES/INDEXES, HOSTING, DOMAINS, INTEGRATIONS, BROWSER-LOCAL.
6. Никогда не отправляй персональные данные и токены в публичные репозитории, логи, чат без необходимости. Для приватного полного архива требуется шифрование, а ключ хранится отдельно.
7. Устанавливай первоначально на НОВЫЕ тестовые аккаунты/проекты; не перезаписывай живые данные.
8. Исполни test suite, затем проверь UI/доступы/содержимое, сравни количество документов и размеры, проверь пробную запись и повторный вход. Только после этого предложи владельцу переключение домена.

## ПЛАН ПОЛНОГО ВОССТАНОВЛЕНИЯ
A. Инвентаризация. Прочти манифест и список component snapshots. Подготовь таблицу «обнаружен / checksum / восстановлен / протестирован».
B. Код. Из директории site/ восстанови структуру файлов на новый приватный Git-репозиторий, НЕ копируя в публичный репозиторий личные данные. Публичный хостинг на HTTPS с верными путями и SW scope.
C. Авторизация. Создай новый Firebase проект; настрой соответствующие OAuth providers и allowed domains; импортируй AUTH export только при доказанном наличии поддерживаемого формата. Некоторые пароли, OAuth-токены и прежние сеансы перенести нельзя: пользователям потребуется повторный вход.
D. Данные. Импортируй проверенный Firestore export (включая типы, имена документов, вложенные коллекции) с остановкой при несоответствии схемы/счётчиков. Применяй и проверь реально заархивированные Rules и Indexes, а не исторические версии.
E. Медиа и дополнительные хранилища. Восстанови файлы из бинарных снимков и заново привяжи идентификаторы к записям. Для Google Drive/Sheets и Cloudflare D1 используй отдельные приватные export sections и их manifests; не считать наличие URL сохранением содержимого.
F. Конфигурация. Восстанови незасекреченные значения. Секреты и ключи владельцу придётся безопасно предоставить из ОТДЕЛЬНОГО хранилища; старые токены лучше перевыпустить. Проверь DNS, сертификат, Google OAuth, Firebase domains и лимиты.
G. Проверки. Сверь построчно количество записей (включая дочерние коллекции), checksum медиа, контрольные записи, права чтения, офлайн-режим и браузеры. Не включай production до согласия владельца.
H. Передача. Создай новый полный архив уже работающей системы и обнови руководство для следующего возможного восстановления.

## ТРЕБОВАНИЯ К БУДУЩЕЙ ПОЛНОЙ КОПИИ
Один зашифрованный переносимый контейнер с манифестом, исходным кодом и полным содержимым независимых exports.
- /site/ — исходники, статика, тесты, конфигурация без секретов, документация.
- /data/firestore/ — типизированный экспорт Firestore и список полных путей документов.
- /data/auth/ — разрешённый экспорт пользователей Auth, роль владельца и формат импорта.
- /data/other/ — Google Sheets, Cloudflare D1 и другие data services, где применимо.
- /media/ — бинарные файлы (фотографии, аудио, обложки) со списком, размерами, hashes и исходными связями.
- /deployment/ — rules, indexes, инфраструктура, версии и инструкции авторизации сервисов.
- /verification/ — SHA-256, количество документов, отчёт полного dry-run восстановления.
- START_HERE_DISASTER_RECOVERY_RU.md — этот файл в КОРНЕ архива.
Каждый отсутствующий компонент обязан быть явно помечен INCOMPLETE. Полнота и тест должны быть подтверждены автоматически и независимым восстановлением.
