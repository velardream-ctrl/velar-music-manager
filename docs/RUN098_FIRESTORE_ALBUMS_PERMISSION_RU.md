# RUN-098 — отказ Firestore при сохранении черновика после добавления «Альбомов»

Дата: 12 ноября 2026. Пользователь показал на iPhone страницу Studio «Главная страница»: статус «Сохранено на устройстве · ожидает синхронизации», сообщение «Черновик не сохранён: Доступ отклонён правилами Firestore», кнопка «Опубликовать» заблокирована. **Черновик не потерян, он локально ожидает записи; фактическую запись в облако пока не подтверждали.**

## Причина, обнаруженная в репозитории

`landing-schema.js` после RUN-096 всегда нормализует **шесть** верхнеуровневых ключей: `hero, artists, albums, releases, genres, about`. Между тем исходный STAGED `firestore.rules` в `validLandingWrite(status)` проверял `content.keys().hasOnly()` и `hasAll()` для прежних **пяти** ключей без `albums`. Поэтому если именно эта версия правил развернута в Firebase, **обе операции create/update для `vmm_public_drafts/landing` и `vmm_public_pages/landing` будут отклоняться**, даже при корректном входе администратора.

В RUN-098 обновлён STAGED `firestore.rules`: `albums` явно разрешён и обязателен в обоих списках, проверяется тип `albums is map`, `albums.entries is list`, максимум 8 элементов. Права `vmm_admins`, закрытых `vmm_catalog`, `vmm_lyrics`, `vmm_links`, анонимное чтение `vmm_public_pages/landing` и запрет всего остального **не менялись**. Регрессионный тест автоматически сравнивает оба allowlist с реальным `normalize(defaults())`.

## Что нужно сделать в живом Firebase (только владелец после проверки!)

1. На iPhone, где открыт Studio, **сначала скачать «резервную копию несинхронизированных изменений» в «Файлы»**. Не удалять сайт, не очищать историю/данные Safari, не нажимать «Обновить из базы» и «Вернуть опубликованную версию».
2. Открыть **Firebase Console → проект `velardream-records-studio` → Firestore Database → Rules**. Проверить, что выбраны правильный проект и **действующая** версия правил (именно published, не вкладка несохранённого черновика). Скопировать полный текст текущих правил в приватную резервную копию до изменения. Ранний backup в `docs/backups/FIRESTORE_ACTIVE_BEFORE_RUN062_2026-11-11.rules` — исторический и не гарантирует совпадения с сегодняшними правилами.
3. Сравнить действующий `validLandingWrite(status)` с обновлённым [firestore.rules](../firestore.rules). **Не заменять целиком продакшн-правила исходником GitHub.** Если в live есть тот же allowlist пяти ключей, точечно добавить `'albums'` в **оба** списка `hasOnly` и `hasAll`, а после проверки `content.artists is map` добавить:
   ```javascript
        && request.resource.data.content.albums is map
        && request.resource.data.content.albums.entries is list
        && request.resource.data.content.albums.entries.size() <= 8
   ```
   Остальные функции, коллекции и запреты сохранить без изменения. Если блок `validLandingWrite` отсутствует либо устроен иначе — остановиться и сравнить полные live rules до правки.
4. Прогнать симуляцию прав: авторизованный администратор с `vmm_admins/{uid}.enabled=true` может записать валидный документ с шестью ключами; анонимный пользователь **не может** читать/писать `vmm_public_drafts` или приватные коллекции, публичное get возможно только для существующего `published` документа; list запрещён. Только после этого нажать **Publish** в Firebase Console. GitHub Pages не разворачивает Firestore Rules.
5. Вернуться на iPhone. При сохранённой локальной копии инициировать повторную синхронизацию (например, коротко отключить и включить интернет, чтобы сработал обработчик `online`). Если статус не изменился — после проверки наличия JSON-бэкапа безопасно перезагрузить Studio, которая должна восстановить IndexedDB и попытаться отправить очередной черновик. **Не пытаться публиковать, пока не появится подтверждение сохранения в облаке.**
6. После надписи «Синхронизировано с облачным черновиком» или «Черновик сохранён (версия N)» проверить состав песен и галочки; затем отдельно нажать **«Опубликовать»**. Если остаётся `permission-denied`, нужны скриншот действующего `validLandingWrite` и проверка администратора/публикации правил. Не открывать приватные коллекции всем пользователям ради устранения ошибки.

## Границы подтверждения

Исправление в GitHub — это **исходник предлагаемых правил**, а не их развертывание в Firebase. Причина подтверждена для исходника репозитория, но **невозможно утверждать**, что реальные live-правила совпадают, пока владелец не покажет действующую конфигурацию. Сообщение на iPhone показывает фактический отказ Firestore. Не считать публикацию восстановленной без реального успешного сохранения и повторной публикации на сайте.
