# VELARDREAM / Smart Site — единый центр распределения и локальный умный поиск

**Статус:** архитектура и задачи, **не реализовано в живой админке**.
**Дата:** 2026-11-13.
**Инициатор концепции:** Илья Дмитриев.
**Задачи:** [#68 — Распределение песен](https://github.com/velardream-ctrl/velar-music-manager/issues/68); [#69 — Умный сайт](https://github.com/velardream-ctrl/velar-music-manager/issues/69).

## 1. Стратегический принцип

«Умный сайт» — стандарт разработки VELARDREAM и ориентир для последующих проектов: интерфейс понимает структуру собственных разрешённых данных, умеет искать, объяснять связи и рекомендовать действия без обязательной оплаты API, но **не подменяет редактора, не публикует самовольно и не выдумывает сведения**.

Умность по уровням:
1. **Инвентаризация**: видно, что уже хранится, где используется и что требует внимания.
2. **Индексация**: можно найти песню по заголовку, слову, фразе, стилю, тематике и проверенному идентификатору.
3. **Объяснимые рекомендации**: система предлагает темы, жанры, настроение или связанную песню и показывает основания.
4. **Управляемая автоматизация**: пакетные изменения, предпросмотр, подтверждение, история и безопасный откат.
5. **Дополнительный ИИ в будущем**: подключаемый сменный модуль, не обязательный для работы сайта.

## 2. Текущая архитектура (подтверждена кодом, не чтением живой базы)

- **`vmm_catalog`** — приватный каталог с `id`, `title`, `artist`, `links.spotify` / `links.youtube`. Studio читает до 1200 документов после проверки полномочий администратора; нельзя делать этот каталог публичным или загружать неполную выборку как полный список.
- **`vmm_public_drafts/landing`** / опубликованный **`vmm_public_pages/landing`** — общий черновик и отдельная публикация. Назначения: `genres.topics.entries[].tracks`, `genres.languages.entries[].tracks`, `albums.entries[].tracks`, `artists.cards[].featuredTracks`. В проекте уже есть `attachedSongSources`, `attachedFind`, `attachedBuildSong`, `attachedReplace` и нормализатор `landing-schema.js`. Нужно переиспользовать их, не хранить вторые назначения.
- **`vmm_links/artist_track_assignments_v1`** — отдельная, версионированная привязка каталоговой песни к артисту. Не смешивать с транзакцией черновика: связь может отличаться по жизненному циклу и локальному outbox.
- **`genres.tags`** — список *названий* жанров; в текущем коде не является привязкой конкретных песен. Отдельно решить, нужны ли «жанры песни» как атрибут в будущем.
- **`vmm_lyrics`** — отдельные приватные тексты и версии. Не индексировать в публичном сайте по умолчанию, не цитировать без явной авторской публикации.
- **Стили Suno**: наличие полноценного сохранённого поля style-prompt в текущей базе не подтверждено. На первом этапе — спроектировать опциональный ввод в закрытой Studio, а не утверждать, что исторические промпты уже существуют.

## 3. Новая вкладка «Распределение песен» (Issue #68)

Разместить в `Studio → Главная страница` рядом с существующими вкладками, **не удаляя и не заменяя** редакторы тем, языков, альбомов или артистов.

### Каталог-матрица

Одна строка = одна **каталоговая композиция** со стабильным ID. Поля: название, исполнитель, наличие официальных ссылок Spotify/YouTube, текущий артист, лучшие песни, все назначения по темам/языкам/альбомам; для каждого назначения показывать группу, название, скрытую/видимую публикацию и, по запросу, черновик versus опубликованное.

Пример: **«Дикая вишня»** — «Артист: Илья Дмитриев», «Тема: Любовь», «Тема: Лирика», «Альбом: ...» (примеры, **не реальные данные Firebase**).

- Поиск по названию, исполнителю, официальной ссылке и ID; фильтры «все», «не назначено», «несколько назначений», «конкретная тема/альбом/язык», «скрыто».
- Показ результата постранично/виртуализированно (например, по 30–40 строк), сортировка по алфавиту, закреплённый поиск. Галочка/чип не должна смещать экран.
- Назначить/снять категорию **в той же строке**; видимые чипы с `×` и компактный выбор групп. Сохранять источники Spotify/YouTube и ограничения 300 песен на подборку; существующие правила 3 лучших песен на артиста. Если официальной ссылки нет, показывать песню в списке, но отключать создание публичной медиапривязки с понятной причиной.
- Для разных песен с одинаковым названием не объединять записи по одному названию: идентификация по ID + верифицированным URL; выявлять неразрешимые неоднозначности и останавливать операцию.
- Сохранение обычного назначения — **только в текущем landing-черновике**, через его имеющиеся IndexedDB offline/outbox и `RUN-108` conflict-safe merge. Не вызывать публикацию автоматически. Кнопки `Сохранить черновик` и `Опубликовать` остаются отдельными.
- Привязка **артиста** — отдельная авторизованная запись с контролем версии `vmm_links`, собственной очередью и возможностью отмены; нельзя притворяться, что одно сохранение landing draft обновляет все источники.
- Показывать различие **«назначено в черновике» / «видно посетителям в опубликованной версии»**. Скрытые темы/альбомы не считать уже публичными.
- На первом релизе полезна read-only сводка + фильтры, затем точечное редактирование, затем (отдельно) безопасные пакетные операции с предварительным просмотром.

### Приёмка

Тестировать: совпадение названий разных артистов; две площадки одной песни; отсутствие URL; 300+ треков; скрытые группы; новый offline draft с конфликтом версий; и существующие неопубликованные данные с телефона. Одна правка не должна менять чужие группы. На iPhone/iPad — без смещения, горизонтальной утечки и потери позиции поиска.

## 4. Smart Index / Smart Tagger (Issue #69)

### Данные и разрешения

`SongIndexEntry`: `catalogId`, canonical title, artist, published links, приватные reference IDs текстов, языковые варианты, опциональный author-approved style prompt, ручные темы, машинные предложения с confidence/evidence, `sourceRevision`, `visibility`, версия индексатора.

**Два логически раздельных индекса:**
- **Административный**, доступен только после Firebase Auth + разрешения `vmm_admins`; построение в браузере из разрешённых данных, локальное кеширование в персональном IndexedDB, безопасная очистка при смене аккаунта. Никаких запросов к платному AI.
- **Публичный**, содержит **только специально опубликованные и разрешённые** метаданные/цитаты. Нельзя автоматически переносить все `vmm_lyrics` или личные черновики в public bundle, Firestore public pages или search engine.

### Поиск по словам и фразам

Нормализовать Unicode, регистр, е/ё и знаки препинания; аккуратно работать с кириллицей, финским и английским, различать точное совпадение и приближённое, индексировать реальные слова и песни, использовать локальный обратный индекс (при необходимости TF-IDF/BM25). Пример: ввод «хопа» → список **действительно совпадающих** песен + проверяемый фрагмент и ссылка на разрешённый плеер. Если совпадения нет — честно сообщать, не выдумывать песню.

### Предложения категорий

Набор независимых сигналов с объяснением:
- **Текст:** выбранные тематические слова/фразы, отрицания, контекст, повторяемость, язык; короткие строки не равны автоматически настроению всей песни.
- **Suno style prompt:** указания `dance`, `slow`, `ballad`, `humorous` и т. п. — признаки *заявленного* стиля, не подтверждённая характеристика звучащего аудио.
- **Ручные назначения владельца** — основной авторитет и источник калибровки, а не повод переопределять его редакторские решения.

Показывать пример: `Рекомендуем: Танцы (0.76) — в стилевом описании есть «dance-pop»`, кнопки «Добавить», «Отклонить», «Почему?». Никакой автопубликации или молчаливой переразметки.

**Темп/BPM**: из самого текста и описания `energetic` настоящий BPM не установить; если автор явно указал `120 BPM`, это метаданные заявленного темпа. Реальный BPM определяется отдельным анализом аудио, если будет такая функция и разрешённый доступ к файлу. Не вводить ложную точность.

### DJ Velar: публичный ответ

По запросу «была песня со словом ...» помощник обращается лишь к опубликованному поисковому индексу, возвращает реальные совпадения, название, ссылку на карточку/официальный плеер. Не делать скрытые Firestore-чтения приватных текстов с клиента, не запускать песни автоматически и не отправлять фразы посетителей в платный сторонний сервис.

## 5. Перенос на другие проекты

Реализовать движок как компоненты с чёткими границами: `SourceAdapter` (право чтения), `Extractor`, `Normalizer`, `Indexer`, `Search`, `Recommender`, `Explain`, `ReviewQueue`, `Publisher`. Отдельно — контроль версий источников и индексных снимков; лог действий владельца без пользовательского слежения.

Для правового/учебного сайта: вместо песен индекс документов/параграфов; сохранять источник, номер статьи, редакцию, юрисдикцию и дату действия. Помощник должен выдавать точную ссылку только на реально найденный источник и отмечать устаревшие нормы/неясности. Генерация «похожей» статьи без подтверждённого источника запрещена.

## 6. Защита и границы

- Нет платных сервисов, обязательных LLM-запросов, доступа к закрытым Drive URL с публичной страницы.
- Нет модификации Firebase Rules/живой базы без отдельной необходимости и подтверждения.
- Нет автоматического объединения конфликтующих черновиков или потери IndexedDB; сохранять RUN-108.
- По умолчанию рекомендации требуют одобрения; список исключений и отмену действий хранить в журнале редактора.
- Индекс всегда можно восстановить из источника; он **не** является единственной копией исходных текстов или музыки.
- Форматы/модули должны работать без сети на ранее загруженных данных и на старых браузерах в пределах существующих ограничений проекта.

## 7. Последовательность реализации

**A — Визуализация назначений:** read-only сводка по всем песням + безопасные фильтры; владелец видит реальную ситуацию и повторы.

**B — Быстрое редактирование:** чипы +/- и точечные привязки в существующие документы, отдельные черновик/публикация и корректная работа offline.

**C — Персональная локальная индексация:** поиск по названиям, словам и фразам, точное сопоставление со всеми версиями текстов, диагностика отсутствующих источников.

**D — Объяснимые тематические подсказки:** тексты + явно хранимые Suno styles, тестовая словарная модель и шкала уверенности, очередь ручного утверждения.

**E — Публичный DJ Velar:** только разрешённый мини-индекс. После появления реальных данных измерять качество выдачи, не выводить искусственную уверенность.

**F — Библиотека Smart Site:** документированный многоразовый модуль для других проектов.

Каждый этап — новый RUN с тестами, журналом «начал/завершил», CI и ручной приёмкой iOS. **Эта спецификация сама по себе не вносит изменений в существующий интерфейс и Firestore**.
