# RUN-085 — Восстановление истории по письмам GitHub («хлебные крошки»)

**Дата анализа:** 12.11.2026, время Europe/Helsinki. **Статус:** первый подтверждённый проход по почтовым уведомлениям + сопоставление с GitHub. **Это не полный архив переписки**, не экспорт Gmail и не подтверждение правильной работы сайта на устройстве.

## 1. Открытие владельца

Владелец обнаружил, что уведомления на адресе проекта образуют **независимую хронологическую цепочку**. Темы писем GitHub содержат репозиторий, название workflow, ветку или заголовок PR, короткий SHA и результат проверки. Они сохраняют промежуточные **провалы CI**, которые в итоговых документах иногда обозначены только фразой «тесты прошли после исправления».

**Правильная схема восстановления:**

1. Из приватного подключённого Gmail искать по месяцам и репозиториям: уведомления GitHub, названия проектов, Issues/PR, workflow/Actions, Pages. Собирать только метаданные, относящиеся к разработке, не всю личную переписку.
2. Нормализовать дату: письмо может показывать часовой пояс отправителя, Gmail или UTC. Для хронологии использовать точную дату workflow/коммита GitHub и обозначать Europe/Helsinki отдельно. Не приравнивать дату доставки письма к дате события.
3. Из темы выделять проект, ветку, короткий SHA, workflow и результат. Открывать связанный **публичный** run по обычной ссылке `https://github.com/<owner>/<repo>/actions/runs/<id>` — **без** Gmail `email_token` и других персональных параметров.
4. Проверять, существует ли полный SHA в истории Git, PR, Actions, подтверждать результаты тестовых job и последующий merge. Уведомления о `PR run failed` и `Run failed` для одной и той же ревизии — часто два письма об одном изменении, **не два независимых изменения**.
5. Устанавливать разницу: **проверка упала** / **изменения в ветке** / **PR слит** / **Pages опубликован** / **пользователь проверил работу**. Эти состояния не взаимозаменяемы.
6. Сопоставить с существующими `WORK_ACTIVITY_LOG`, `PROJECT_HANDOFF`, GitHub Issue, roadmap, архивами Google Drive/Apps Script. Записывать **только недостающие подтверждённые этапы**, а расхождения — как отдельные пометки с датой, не переписывая историю задним числом.
7. Историю переписок, код или личную базу не «восстанавливать» из почтовых заголовков: для этого нужны соответствующие Git коммиты и резервные копии данных. Не хранить письма, Gmail IDs, личные токены и коды входа в публичном GitHub.

## 4. Необходимая следующая работа по восстановлению всей истории

1. Пройти почту **порциями по датам и каждому репозиторию**, включая отдельные поиски PR/issues, GitHub workflow и Pages, не только failures. Для каждого периода считать количество полученных сообщений, признак `next_page_token` и наличие пробелов. Не публиковать личные письма.
2. Составить **машинно-сопоставимый индекс**: дата GitHub UTC, проект, RUN, ветка, полный Git SHA (если найден), PR, workflow run ID, тип доказательства, исходный документ, `confirmed / incomplete / conflict`. Почтовый Gmail ID **не публиковать**, хранить только в закрытом рабочем источнике, если понадобится.
3. Выгрузить/проверить историю коммитов GitHub до первой даты, по которой есть письма. Для Sanastoyhteisö старый Apps Script/Google Sheets и историю Drive версии проверять отдельно: почта GitHub не заменит этапы до появления Git репозитория.
4. Сверить с `WORK_ACTIVITY_LOG` всех проектов, не склеивать production Sanastoyhteisö с `riveria-sanasto-community-test`; несогласованные статусы отмечать как факты с двумя ссылками.
5. После нового подтверждения дополнять **соответствующий** Work Log каждого проекта, а не только музыкальный журнал. Этот файл — межпроектная методика, не новая «единая база данных» всех проектов.
6. Ничего не удалять из Gmail и не менять архивные письма. Не использовать приватные параметры ссылок с `email_token` в публичных заметках.

## 5. Новый незакрытый дефект интерфейса — по сообщению владельца

**ОЖИДАЕТ СКРИНШОТОВ И ПРОВЕРКИ НА УСТРОЙСТВАХ:**
- На старом iPad и нынешнем iPhone есть различия в отображении VELARDREAM.
- На iPhone пользователя **не работает анимация посимвольной печати сообщений VELAR**, хотя RUN-082 имел успешные автоматические тесты и Pages deployment.
- Воспроизведение пока не получено; нет оснований объявлять причину. Проверять `prefers-reduced-motion`, конфигурацию `genres.assistant.typing`, кэш PWA/SW, обработку `setTimeout`, версию Safari и реальные скриншоты. Нельзя молча выключить функцию или объявить её исправленной без проверки.
- Не смешивать проблему сайта с неисправностью GitHub Actions: CI проверял имитацию браузера, не реальное устройство. Когда пользователь пришлёт скриншоты, открыть новый RUN диагностики и описать симптомы с временем/URL/контекстом (Safari либо иконка PWA), не публикуя приватный скриншот.

## 6. Что считается доказательством

| Доказательство | Подтверждает | Не подтверждает |
|---|---|---|
| Письмо GitHub | Пользователь получил уведомление о событии, ветке, коммите или проверке | Что итоговый сайт работает, что это единственный запуск или полная история |
| Git commit | Код/документы существовали в зафиксированном состоянии | Что именно этот код опубликован и реально выполняется на устройстве |
| PR merge | Изменение попало в конкретную основную ветку | Прохождение защитных тестов, наличие рабочих данных, Safari UX |
| Actions run | Результат конкретного workflow и каждого job | Все остальные workflows, реальную Firebase Console, пользовательское устройство |
| Pages success | Статическая версия опубликована сервисом Pages | Эффект печати, права Firestore, изображения, офлайн-кэш на старом iPad |
| Ручной тест на устройстве | Конкретная функция работала/не работала в данной среде | Что нет ошибок в других браузерах, аккаунтах, сценариях |

**Правило для каждого следующего чата:** Gmail — свидетель и навигатор; GitHub — источник истины о коде; Firestore/Drive — собственные базы; владелец на устройстве — подтверждение интерфейса. Никаких необоснованных «всё восстановлено».
