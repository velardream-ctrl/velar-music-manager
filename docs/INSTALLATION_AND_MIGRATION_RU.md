## I. ДВА РАЗНЫХ СЦЕНАРИЯ

### A — восстановить тот же VELARDREAM после поломки

Требуются **старые** домен/репозиторий/Firebase/Drive и соответствующие права. Восстанавливать код безопасно через GitHub commit/tag/revert, **не перезаписывая** приватные документы и не изменяя Google Drive. Сначала установить, где сбой: Pages, версия CSS/JS/Service Worker, авторизация, Firestore Rules, черновик/публикация, Drive, локальный IndexedDB. Не использовать восстановление публичного HTML вместо резервирования Firestore.

### B — создать **новый** сайт на том же подходе

Требуются **новые** идентичность проекта, репозиторий, домен/поддомен, Firebase Auth + Rules + collections, Drive и права. Взять **копию кода** и выбрать/настроить модули. Запрещено копировать чужие записи Firestore, UID, приватную папку Drive, ключи и персональные изображения. Для Sanastoyhteisö сначала провести отдельный аудит образовательных схем и пользователей: это не музыкальный каталог.

## II. БАЗОВЫЕ ПРЕДПОСЫЛКИ

1. Доступ к GitHub исходного проекта и права создавать **новый** репозиторий/ветку. В данном проекте основной код в `main`, GitHub Pages публикует статический корень.
2. Точное имя домена/предполагаемый base path. Ряд URL и Service Worker текущего сайта рассчитаны на корень домена; при размещении в подкаталоге эти пути надо проверить отдельно.
3. Для кода/тестов: Node.js >=18, CI на Node 20. В `package.json` нет обычных npm-зависимостей; `npm test` вызывает встроенные node-тесты. Для локальной проверки Web API нужен статический HTTP-сервер и браузер, а не `file://`.
4. Отдельный проект Firebase и контроль права Google-администратора; текущая публичная клиентская конфигурация относится к **`velardream-records-studio`**. Для нового сайта создать **новую** конфигурацию.
5. Только при использовании приватных фонограмм: отдельная Google Drive папка, Google OAuth и выбранный правильный аккаунт, разрешение `drive.file`.
6. **Необходимый бэкап** всех сохраняемых данных и контроль точных количеств документов/файлов **до** любой миграции. Правила проекта `firestore.rules` нельзя считать автоматически развёрнутыми.

## III. ПОЛУЧИТЬ КОД И ЗАПУСТИТЬ ТЕСТЫ

На компьютере, где доступен Git:

```sh
git clone https://github.com/velardream-ctrl/velar-music-manager.git
cd velar-music-manager
git status --short
git log -1 --format='%h %ci %s'
npm test
node --check main.js
node --check sw.js
```

Это **читает публичный код**, не переносит личные Firestore/Drive данные. Когда на устройстве нельзя поставить Node/Git, использовать GitHub UI/PR и штатный GitHub Actions — он уже запускает `npm test`. Не объявлять тесты пройденными, если Actions красный/отменён/в очереди.

Для локального рендеринга статической части можно выполнить `python3 -m http.server 8000` и открыть `http://localhost:8000/`. **Ограничение:** Google Auth, Secure Context Service Worker, OAuth, разрешённые домены Firebase и интеграции не обязаны работать на этом адресе без отдельной настройки. Отладочная страница не доказывает успешное развёртывание.

## IV. СДЕЛАТЬ КОПИЮ САЙТА БЕЗ СМЕШЕНИЯ ДАННЫХ

### 1. Репозиторий и права

- Создать новый репозиторий/копию в GitHub. Рекомендуемый будущий механизм — Template Repository, но в 11.2026 **он ещё не подготовлен**. Сейчас делать копию исходников без переноса истории приватных интеграций и без исходных бэкапов в новую публичную папку.
- Не направлять копию обратно на исходную ветку `main` VELARDREAM; работы нового сайта не должны менять старый.
- Включить Action CI в новом репозитории. Для Pages задать источник публикации и проверить новый URL, HTTPS и доступность статических файлов.

### 2. Имя, домен, тема и визуальные активы

Проверить и заменить в **новом** репозитории:
- `CNAME` — удалить или изменить на новый проверенный домен. Если оставить `velardream.com`, новая копия может пытаться использовать исходный домен.
- `manifest.webmanifest`: `name`, `short_name`, `description`, `start_url`, `scope`, цвет и иконки.
- `index.html`, `studio/index.html`, `app/index.html`: заголовки, меню, язык, брендинг, сообщения, favicon.
- `style.css`, `studio/studio.css`, `studio/recordings.css`, `assets/`: шрифты, логотипы, фотографии и цвета; не распространять не разрешённые новым владельцем аватарки/арт.
- `landing-schema.js`: базовые публичные заголовки/структуры, разделы, темы/языки, музыкальные пресеты. Сейчас часть музыкальных defaults жёстко заложена; **до универсального шаблона это нужно вынести в конфигурацию**.
- Публичные интеграции `landing-public.js`, `universe.js`, `languages-public.js`, `topics-public.js`, `velar-assistant.js`: решить, какие нужны новому сайту. Не отключать связанные модули простым удалением файла без проверки script tags и тестов.

**Не удалять `noindex`** в исходном VELARDREAM автоматически. В новом сайте политика индексации — отдельное решение владельца после завершения тестов. Не считать SEO-метатег паролем.

### 3. Firebase изолировать с нуля

1. В Firebase Console создать отдельный проект, настроить Authentication Google, Web App и Authorized Domains **нового** сайта. Публичный Firebase Web Config нового проекта вставить в **копию** `studio/firebase-config.js` (или будущий installer-конфиг); не использовать старую конфигурацию.
2. Создать Firestore с закрытыми правилами. Сравнить актуальные rules нового проекта с моделью `firestore.rules`; **этот файл STAGED**, его нельзя бездумно разворачивать на существующий живой проект. Настроить серверное `vmm_admins/{uid}` вручную уполномоченным владельцем.
3. Проверить **положительный** сценарий: разрешённый Google аккаунт после входа видит Studio и читает нужные записи. Проверить **отрицательные**: чужой Google аккаунт не читает коллекции, анонимный не может листать приватные документы, публичный `landing` читается только после подтверждённой публикации.
4. Создать/инициализировать пустые данные или выполнить **проверенную** миграцию с отдельным источником. НЕ переносить существующие UID, персональные адреса, тексты, контакты и аудио только потому, что они были в образце.
5. В новом контексте переименовать/сконфигурировать коллекции под предметную область. Перенос `vmm_catalog` в образовательный сайт требует **новой схемы**, а не замены слова «песня» на «слово».

### 4. Публичная CMS и публикация

- Админ-редактор `studio/landing-editor.js` хранит черновик в `vmm_public_drafts/landing`; явная публикация записывает `vmm_public_pages/landing`. На публичном сайте `landing-public.js` читает только подтверждённый документ.
- При переносе оставить две стадии **сохранить → опубликовать** и транзакционное сравнение `revision`, иначе один администратор может затереть другой.
- Настройки помощника (RUN-080), радио, кнопок и изображений — **публичные данные после явной публикации**. Никогда не помещать в их поля приватные ссылки Drive/личные тексты/секретные ключи.
- Если на новом сайте нет Firestore/правил, публичная страница может показать исходный **статический fallback**. Это допустимо как безопасная временная версия, но не значит, что CMS работает.

### 5. Google Drive / фонограммы / офлайн

- Подключать Google Drive только если новый сайт действительно работает с приватными файлами. В VMM используется `drive.file` и папка `VELARDREAM RECORDS - Фонограммы`; новый сайт **не должен использовать эту же папку**.
- Не копировать `vmm_recordings` без соответствующих приватных Drive файлов и подтверждённого права доступа; метаданные не заменяют аудио.
- IndexedDB `velar-audio-repertoire-v1` / caches имеют привязку к origin и UID. У новой копии будет своё хранилище браузера, не общий offline набор. Не трактовать кэш устройства как долгосрочную резервную копию.
- Service Worker `sw.js` имеет публичный и студийный белый список. При переименовании скрипта/папки/домена изменить **все** версии и пути в precache, HTML и тестах. Нельзя кэшировать приватные API-ответы, auth или Drive media.

## V. ПРОВЕРКИ ПЕРЕД ОТКРЫТИЕМ НОВОЙ КОПИИ

**Программные:**
- `npm test` полностью SUCCESS; node --check для затронутых JS; GitHub Actions на PR/новом `main` SUCCESS.
- Новые значения конфигурации проходят нормализацию/валидацию; legacy-документы мигрируют без потери настроек.
- Предусмотрен rollback (Git tag/commit + backup DB); частные данные не попали в zip/публичный репозиторий.

**Безопасность:**
- Неавторизованный пользователь не может читать `vmm_lyrics`, `vmm_catalog`, `vmm_recordings`, `vmm_contacts`; одобрение администратора — серверное.
- Публичный сайт читает только явно опубликованные поля, никогда private Drive URLs.
- Новая админка не позволяет подменять iframe произвольными URL, вносить скрипты в HTML, запускать аудио автоматически или обходить права через client-side скрипт.
- В Firestore Console сохранён факт deployed rules и дата; это **не** доказывается GitHub YAML.

**Устройства:**
- iPhone Safari и добавление на экран домой (PWA), с учётом safe-area/клавиатуры и сброса устаревшего SW.
- Старый Safari 12 / iPad и Android/Samsung: формы, выпадающие списки, рисунки, доступность, шрифты, fallback форматов.
- При потере сети: статический fallback, сохранённый офлайн-медиа, корректные предупреждения при неотправленной записи, отсутствие ложных «успешно».
- Для музыки: ручной запуск плеера, никакого autoplay.
- Для чата: сохранность десяти оригинальных изображений и выбор эмоций, 0–12 тегов, отсутствие облачного AI/хранения сообщений.

## VI. КАК РАЗВИВАТЬ НАСТОЯЩИЙ ШАБЛОН / СВОЙ ДВИЖОК

Сейчас файлы можно копировать **технически**, но десятки значений и предметные имена ещё привязаны к VMM; самостоятельный installer **не реализован**. Дорожная карта:

- **Core**: навигация/доступ/аудит/CRUD/schema/миграции/offline.
- **Theme**: бренд, CSS-токены, лого, цвета, меню, языки, видимые надписи и аватары.
- **Modules**: музыка, учёба/словари, таблицы, радио и другое — отдельные плагины/адаптеры, не общий несвязный файл.
- **Adapters**: Firebase/Auth/Firestore, Google Drive, IndexedDB/Cache, экспорт/бэкапы.
- **Installer**: проверка домена, безопасный мастер выбора модулей, проверка правил, тест пустой инсталляции, экспорт/импорт конфигурации, отказ при несоответствии.
- **Release**: версия движка/схемы, шаблон репозитория, автоматические smoke тесты, план обновления/отката и журнал каждого экземпляра.

**Sanastoyhteisö** — образовательная платформа с собственными словарями/пользователями/экзаменами; её адаптация должна сохранить роль/права/прогресс учащихся. Нельзя просто скопировать `vmm_lyrics` или музыкальные `vmm_admins` в её Firebase. После аудита отдельно определить публичные словари, приватный прогресс и админские настройки.

## VII. АВАРИЙНОЕ ВОССТАНОВЛЕНИЕ / ПОСЛЕДОВАТЕЛЬНОСТЬ ДЛЯ НОВОГО ЧАТА

1. Открыть `docs/MASTER_PROJECT_MAP_AND_HANDOFF_RU.md`, `docs/PROJECT_HANDOFF_RU.md`, последние **датированные** записи `docs/WORK_ACTIVITY_LOG_RU.md`.
2. Сверить GitHub main SHA/PR/Actions/Pages; если предыдущая сессия прервалась после `create_commit`, проверить **branch ref**, а не создавать дублирующую правку.
3. Выяснить, что именно исчезло: код HTML/JS, разрешение Firebase, публикация CMS, приватные аудио Drive, локальный IndexedDB/кэш.
4. Сохранить перед восстановлением копии исходных данных/правил, при необходимости открыть отдельный PR только на код; не менять права/документы «наугад».
5. Прогнать регрессионные тесты и проверить устройство; отметить НАЧАЛ / ПРОВЕРКА / ЗАВЕРШИЛ или ОЖИДАЕТ в **том же** Work Log.
6. Обновить короткий handoff: точная точка продолжения и новые риски; не писать «всё работает», если фактический Firebase/Drive не проверен.

**Постоянная фраза нового чата** находится в [главной карте, раздел 0](MASTER_PROJECT_MAP_AND_HANDOFF_RU.md). **Главный принцип:** переносим **движок и знания**, а не секреты и чужую базу.
