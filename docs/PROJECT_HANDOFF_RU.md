# VELARDREAM — инструкция для нового чата, разработчика или агента

Этот документ — **точка входа** для продолжения проекта без потери решений.

## 1. Где всё находится
- Канонический репозиторий: https://github.com/velardream-ctrl/velar-music-manager
- Живой сайт: https://velardream.com/ и закрытый интерфейс (публичный HTML, защищённые данные) https://velardream.com/studio/
- Журнал: [WORK_ACTIVITY_LOG_RU.md](WORK_ACTIVITY_LOG_RU.md)
- План независимого шаблона: [REUSABLE_SITE_TEMPLATE_RU.md](REUSABLE_SITE_TEMPLATE_RU.md)
- Доступы: Firebase Auth через Google, разрешённый `vmm_admins/{uid}`; Firestore коллекции `vmm_catalog`, `vmm_lyrics`, `vmm_recordings`, `vmm_audit`; фонограммы — личный Google Drive, не публичные MP3 URL.
- **Никаких паролей, OAuth-токенов и личных данных в GitHub.** Web Firebase config публичен и сам по себе не даёт прав на базу.

## 2. Что читать прежде всего
1. `docs/WORK_ACTIVITY_LOG_RU.md`: последние RUN и известные регрессии.
2. `README_RU.md`, `docs/PRIVATE_STUDIO_SETUP_RU.md` — исторический контекст; в них есть устаревшие этапы с датой 9 ноября, не воспринимать их как текущий статус.
3. `studio/index.html` и модули `studio/studio.js`, `studio/workflows.js`, `studio/recordings.js`, `studio/offline-repertoire.js`, `studio/lyrics-tools.js`, `studio/print-export.js`.
4. `sw.js` (безопасный кеш **только** статических файлов), `studio/studio.css`, `studio/recordings.css`.
5. `firestore.rules` — файл-образец, а не доказательство реально развёрнутых правил.
6. `package.json` и тесты в `tests/`; затем список открытых PR и CI.

## 3. Обязательная последовательность работы
**НАЧАЛ** → понять точный симптом → проверить активную ветку, последние CI и пользовательский скриншот → новая ветка `fix/runNNN-...` → минимальный патч → регрессионный тест → CI → сверить новые статические версии в `studio/index.html` и `sw.js` → PR → **только после успешных проверок и разрешения на публикацию** merge → реальная проверка iPhone → **ЗАВЕРШИЛ** / «ожидает проверки». Внести обе границы и ссылки в журнал.

При незавершённом PR работу возобновлять **в нём**, а не создавать вторую конкурирующую правку. Если CI упал — смотреть конкретный failed step, не менять приложение наугад. Обновление кеш-версий должно быть атомарным.

## 4. Что нельзя ломать
- Заголовок/UPC/каталожная строка песни при редактировании текста, связь версий и многосрочный текст; проверка несохранённых изменений.
- Сторонние Google-аккаунты не получают данные. Не использовать самопроверку администратора на стороне клиента вместо Firestore Security Rules.
- Не публиковать тексты, аудио, контакты или резервные JSON в репозитории, в публичном Service Worker или в логах.
- Офлайн-галочка управляет **локальной** копией; удаление записи должно быть обратимым и не затрагивать песню или текст. Исправление ошибок загрузки не должно уничтожать уже загруженные файлы.
- Тексты + фонограммы доступны как два режима чтения (A4 две колонки / крупный текст).
- Работоспособность на iPhone Safari и в режиме «Добавить на экран Домой»; отдельно учитывать нижнюю safe area.

## 5. Диагностика и контроль
- Исправление считается доказанным в коде только после успешного PR/CI, а в продукте — после проверки на телефоне.
- Ошибка OAuth/Drive: проверить выбор Google-аккаунта, область `drive.file`, API Enabled, токен в памяти, сохранность ID папки. Не помещать токен в client storage.
- Ошибка исчезновения записи: проверить callback `onAuthStateChanged`, вкладку, `songId`, сетевой результат загрузки и Firestore commit. Файл может уже находиться в Drive при ошибке создания индексной записи — **не загружать повторно вслепую**.
- Офлайн: проверять пользовательский IndexedDB, наличие Blob, оболочку Service Worker, авторизацию, повторное открытие без сети и риск очистки iOS.
- Все ошибки фиксировать с RUN, датой, PR, симптомом, причиной, решением и регрессионным тестом.

## 7. RUN-061: публичная главная через безопасную CMS (2026-11-11)

В админ-студии создана вкладка Главная страница (#vmm-landing): первый экран, артисты, музыка/релизы, жанры, о проекте, публикация. Сохраняемый черновик — только vmm_public_drafts/landing; публикуется только vmm_public_pages/landing. На velardream.com скрипт landing-public.js считывает один опубликованный документ и безопасно обновляет текст/карточки; старые статические блоки остаются резервной версией. Общая схема — landing-schema.js; UI — studio/landing-editor.js; тесты tests/test-landing-*.mjs.

**ВНИМАНИЕ: файл firestore.rules в GitHub — STAGED, NOT DEPLOYED.** Применение правил в Firebase обязательно и ещё не подтверждено. Перед публикацией открыть и сохранить действующие rules, затем вручную добавить именно два ограниченных блока и validLandingWrite из этого RUN, не стирая рабочие правила частных коллекций. Полная инструкция: docs/RUN061_FIRESTORE_PUBLICATION_RU.md. До этого редактор может сообщить permission-denied, а публичный сайт продолжит показывать статический текст.

Никаких автоматических публичных выгрузок из vmm_catalog, vmm_lyrics, Google Drive или IndexedDB. Публикуются только введённые администратором карточки, описания, жанры и HTTPS-ссылки с явным нажатием «Опубликовать». Транзакции защищают от конкурирующих перезаписей. Публичный сайт не запрашивает Firebase Auth и не должен иметь прав на private collections.

**После применения правил:** сохранить черновик → убедиться, что landing page не изменился → нажать «Опубликовать» → проверить сайт с обычной анонимной вкладки → проверить работу на iPhone, Android и компьютере; отдельно попробовать посторонний аккаунт, отсутствие сети и защиту от частных ссылок.


## 8. RUN-064: артисты из каталога и ручная привязка песен

В «Главная страница → Артисты» выбор из 3 фиксированных профилей DJ Velar, Илья Дмитриев, Crazy Bobr плюс имена, прочитанные из vmm_catalog. Карточка скрыта до публикации, публичное имя редактируется, artistId стабилен. Кнопка «Назначить песни» открывает приватный список с поиском и чекбоксами, массовым выбором и отдельной транзакционной кнопкой сохранения. **Исходные значения artist/UPC/ISRC, релизные ссылки, лирика, Drive, офлайн-файлы не меняются.**

Исключения из исходного распределения песен (например, исходный Velar → артист сайта Crazy Bobr) хранятся в закрытом документе vmm_links/artist_track_assignments_v1, исключительно в уже существующей admin-only коллекции. Приватная схема: revision, overrides {trackDocId: artistId или unassigned}, updatedBy, updatedAt. Конфликты нескольких устройств выявляются ревизией; подтверждение обязательно при переносе от другого артиста. Служебный документ исключён из списка предложений ссылок в studio/workflows.js. Имена, фоно/lyrics, кредиты дистрибьютора и реальные песни в Firestore не массово мигрированы. Связи не публикуются на landing; на публичной странице только вручную одобренные карточки и релизы.

Инструкция владельцу: docs/RUN064_ARTIST_PICKER_AND_TRACK_ASSIGNMENT_RU.md. Новый модуль studio/artist-track-links.js, источник выбора studio/artist-choices.js; изменения studio/landing-editor.js и landing-schema.js. CI: RUN-064. Ручная проверка на реальном устройстве, применение правил RUN-062 и будущая работа над отдельными публичными страницами артистов остаются открытыми.


## 9. RUN-065: загрузка и кадрирование фотографий артистов (2026-11-11)

В студии Главная страница → Артисты в карточке появились «Загрузить фотографию»/«Заменить», «Убрать фото», квадрат/круг. Модуль studio/artist-image-editor.js открывает браузерный Canvas crop (зум и X/Y), преобразует в WebP/JPEG до ~90KB (вывод до 720px). В landing-schema.js проверяется только data:image/webp/jpeg;base64, лимит одного изображения и общий лимит 780000 символов; landing-public.js показывает круглый/квадратный портрет. Изменения сохраняются только после старых действий сохранить черновик → опубликовать. Тяжёлые исходные файлы никогда не передаются серверу.

Изображения временно включены в уже существующий Firestore документ landing, поэтому никаких новых правил или Firebase Storage (потребовал бы Blaze) в RUN-065 нет. Применение реальных Firestore Rules RUN-062 ранее не подтверждено, поэтому публикация остаётся зависимой от ручной настройки Firebase.
