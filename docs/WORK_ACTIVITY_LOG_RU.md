# VELARDREAM — журнал работ и решений

**Дата актуализации:** 2026-11-11. **Источник истины:** GitHub-репозиторий `velardream-ctrl/velar-music-manager`, ветка `main` плюс открытые PR. Этот журнал — навигация по реальным изменениям, **а не замена Git/CI**.

## Правила ведения
- Каждая значимая работа получает идентификатор `RUN-NNN`, цель и ветку/PR.
- Сразу вносить запись `НАЧАЛ`: проблема, воспроизведение, затронутые файлы, план, риски.
- После изменений вносить `ПРОВЕРКА`: команды и фактический результат CI, ручные проверки, неудачи.
- Запись `ЗАВЕРШИЛ` допустима **только после** слияния PR и проверки основных условий. Если ручная проверка на iPhone ещё нужна, указать это отдельно.
- Любую неудачу, выявленную на реальном устройстве, описывать с симптомом и способом воспроизведения, без личных текстов и токенов.
- Запрещено «исправлять» журнал задним числом с удалением неудач: добавлять новую запись с объяснением.
- Перед новым RUN прочитать [протокол передачи](PROJECT_HANDOFF_RU.md), последние строки этого журнала, PR и результаты CI.

## Как определить реальное состояние
1. Сравнить `main`, открытые PR и GitHub Actions; документы 9 ноября могут быть устаревшими.
2. До каждой публикации запускать `npm test` (Node.js >=18) и смотреть вывод всех тестов. Зелёный CI **не означает** проверенного iPhone/Google OAuth.
3. Смотреть последние наблюдения владельца в этом чате: воспроизведение FLAC для «Дикая вишня» 35,3 МБ на iPhone подтверждено скриншотом; галочка «Офлайн» отображалась, но запуск без интернета ещё не проверен.
4. При ошибке составить последовательность: точный экран → действие → сообщение → версия/PR → сетевые зависимости → последний успешный шаг.
5. Не удалять и не переписывать исходные файлы Google Drive, записи каталога, тексты, историю изменений и резервную копию без явно согласованной миграции.
