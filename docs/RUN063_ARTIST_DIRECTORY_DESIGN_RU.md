# RUN-063 — Единый справочник артистов VELARDREAM (проект решения)

Дата: 2026-11-11
Статус: ПРОЕКТИРОВАНИЕ; БЕЗ МУТАЦИИ КАТАЛОГА И ПУБЛИКАЦИИ
Уточнение владельца: публичное имя — **DJ Velar**, именно латиницей (не «DJ Вилар»).

## Задача владельца
Не вводить вручную существующих артистов на landing page. В админ-панели выбирать готовых исполнителей из приватного каталога, иметь возможность установить единое публичное имя, автоматически связывать их песни. Особенность: часть музыкальных записей **Crazy Bobr** исторически в каталоге и у дистрибьютора записана как **Velar**. Встречаются русское и латинское написания имени Илья Дмитриев. Пользователь хочет три самостоятельных профиля: **DJ Velar**, **Илья Дмитриев**, **Crazy Bobr**.

## Рекомендованная модель

1. Приватный справочник **vmm_artists/{artistId}** (потребует отдельного admin-only правила доступа после анализа фактически опубликованных Firestore Rules):
   - `artistId`: стабильное внутреннее значение, не публичное имя: `velar`, `ilya-dmitriev`, `crazy-bobr`.
   - `displayName`: редактируемое имя для главной: `DJ Velar`, `Илья Дмитриев`, `Crazy Bobr`.
   - `aliases`: альтернативные написания в источниках (только подтверждённые владельцем), например `Velar` и несколько вариантов написания `Илья Дмитриев`; нельзя автоматически считать все песни `Velar` принадлежащими `Crazy Bobr`.
   - `description, imageUrl, publicUrl, sortOrder, visible`: оформление публичной карточки и порядок, HTTPS проверяется при публикации.
   - `createdAt,updatedAt,revision`: аудит и защита от случайного перезаписывания.

2. В каждом приватном документе **vmm_catalog/{trackId}** оставить историческое поле `artist` как получено из исходной таблицы/релиза. Для нужной песни явно установить `siteArtistId` (выбранный ключ артиста). Остальные поля (ID, title, UPC/ISRC, links, lyrics, Drive, локальные offline blobs) не менять. Поддержать массовое присвоение по подтверждённым галочкам. Вместо изменения оригинальных кредитов — обратимое присвоение. При необходимости визуально показывать `Исходный исполнитель → Артист на сайте`.

3. **Каталог → Исполнители**: список всех реальных значений исходного поля `artist` с количеством композиций, нормализацией пробелов/регистра и `ё/е` (а transliteration только после подтверждения); возможность «Создать профиль», «Привязать к существующему», «Выбрать песни Crazy Bobr среди Velar». Каждая песня связана с ровно одним каноническим артистом (коллаборации — отдельная будущая задача). Перед применением изменений показывать старое и новое распределение, сохранять только выбранные trackId, журналировать изменения.

4. **Главная страница → Артисты**: добавить выбор из справочника, а не ввод целого профиля вручную. Допускается редактор публичного заголовка/описания для конкретной карточки; ссылка на artistId не меняется при смене имени. При подготовке публикации собирать *выборочную публичную копию* разрешённых карточек и релизов в `vmm_public_pages/landing` через текущую схему черновика и отдельную кнопку `Опубликовать`.
   - Частные данные исходного каталога целиком никогда не выводить.
   - Привязка всех песен внутри приватного каталога может быть автоматической, но для публичного списка треков нужна отдельная явно подтверждённая видимость. Нельзя автоматически обнародовать неопубликованные работы, закрытые фонограммы или тексты.

## Порядок миграции
1. Прочитать фактическое содержание vmm_catalog после Google-авторизации в админке. Посчитать уникальные имена исполнителей и количество записей.
2. Создать три профиля с отдельными artistId и отредактируемыми displayName.
3. Создать **предварительный** отчёт распределения песен: Velar, Илья Дмитриев (включая подтверждённую латиницу), кандидаты Crazy Bobr. Никаких автоматических необратимых массовых замен.
4. Вручную отметить конкретные песни Crazy Bobr и подтвердить пакетное присвоение; подсветить расхождения исходной метки и `siteArtistId`.
5. Проверить, что sourceRow, UPC, релизные ссылки, lyrics, offline Drive не менялись; сделать backup каталога до первой записи и сохранить в журнал.
6. Обновить выбор артистов в landing CMS из справочника, сохранить черновик, предпросмотреть и только потом опубликовать публичную копию.

## Безопасность и внешние площадки
- Переименование карточки **не меняет** имя артиста у дистрибьютора (Spotify, Apple Music, ISRC/UPC, обложки). Исправление релиза на площадках — отдельная задача через дистрибьютора, если владелец решит её выполнять.
- Никакой автоматической публикации закрытых треков, текстов и фонограмм. Приватный Firestore остаётся приватным.
- **Не менять текущие правила Firebase**, пока пользователь проходит RUN-062 и не подтвердил публикацию и проверку новой публичной коллекции. Для будущей `vmm_artists` потребуется отдельный ограниченный блок доступа только администратору и новая проверка.
- Никакой массовой перезаписи существующего поля `artist` без подтверждения владельца; резервная копия каталога обязательна перед присвоением `siteArtistId`.

## Состояние
Проект структуры подготовлен. Реальные данные Firestore не прочитаны и не изменены; неизвестно точное количество треков каждого исполнителя. Firebase RUN-062 пока не имеет подтверждённого результата публикации. Следующий безопасный шаг — закончить проверку правил Firebase, затем начать с **просмотра и группировки каталога без изменений**.
