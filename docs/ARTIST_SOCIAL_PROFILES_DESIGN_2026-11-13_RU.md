# VELARDREAM Records — система официальных профилей и социальных площадок артистов

**Дата:** 2026-11-13. **Статус:** МАКЕТ / АРХИТЕКТУРА, НЕ РЕАЛИЗОВАНО НА САЙТЕ.  
**Инициатор:** Илья Дмитриев.  
**Проект:** `velardream-ctrl/velar-music-manager`.

## Цель

Одна публичная индексируемая карточка / персональная страница для каждого артиста. Пользователь видит понятные кнопки «Слушать» и «Подписаться»; владелец редактирует официальные ссылки из Studio; поисковые системы получают обычные HTML-ссылки и соответствующие типы Schema.org. Сайт VELARDREAM становится центральной точкой маршрутизации слушателей и продвижения релизов, без дорогостоящих API и стороннего link-in-bio сервиса.

## Выявленные исходные условия (проверено по main 13.11.2026)

- `landing-schema.js`: `artists.cards` — максимум **12 карточек на главной**, стабильный `artistId`, `title`, `subtitle`, `description`, `imageData/imageUrl`, `imageShape`, `featuredTracks`, `visible`; **социальных сетей в карточке пока нет**.
- `studio/landing-editor.js`: Studio → Главная страница → Артисты; раздельные черновик и публикация; связи с песнями хранятся отдельно в `vmm_links`; не смешивать эти системы.
- `landing-public.js`: карточка артиста, фото, описание, кнопка существующей внешней ссылки и лучшие песни; наращивать совместимо.
- `index.html`: `<meta name="robots" content="noindex,nofollow,noarchive">`. **Открытие индексации должно быть отдельным согласованным релизом после аудита.** Действующий HTTP-ответ сайта на этом этапе не подтверждён.
- Совместимость: старый iPad/Safari 12, мобильный iPhone/PWA, основной сайт FI/EN/RU.

## Публичный UX (макет)

1. Из главной витрины «Артисты» слушатель переходит на постоянный URL, например `https://velardream.com/artists/dj-velar/` (это **пример будущего адреса**, маршрут ещё не создан).
2. Вверху: портрет из существующих настроек, имя артиста, краткий жанр/описание, узнаваемая цветовая стилистика VELARDREAM; ниже — биография (публичная, заполненная владельцем).
3. Два визуально ясных блока: **«Слушать музыку»** (Spotify, Apple Music, YouTube Music, SoundCloud, Bandcamp, VK Music, Яндекс Музыка, где доступны официальные профили) и **«Следить за артистом»** (YouTube, Instagram, TikTok, Facebook, Telegram, VK, иные подтверждённые страницы).
4. Дизайн: фирменный тёмно-синий, сдержанное золото; крупные касательные зоны для телефона, название сервиса текстом вместе со значком (не иконка без подписи); выбранная главная CTA-кнопка, остальные — компактные. Не показывать пустые ссылки или несуществующие аккаунты.
5. Дальше — уже существующие лучшие песни, альбомы, клипы. Переход в соцсети в новой вкладке / внешнем приложении с обычным `<a href>` и `rel="noopener noreferrer"`, без переходных трекеров.
6. Служебная ссылка «Поделиться профилем» и копирование **собственного** VELARDREAM URL. В bios социальных сетей использовать этот постоянный адрес, чтобы аудитория возвращалась к VELARDREAM.

## Studio UX

`Studio → Главная страница → Артисты → [выбранный артист] → Социальные сети и площадки`.

Поля: провайдер, полная HTTPS-ссылка, назначение («Слушать» / «Следить»), подтверждение принадлежности аккаунта, видимость, порядок, основная CTA, короткая подпись. Удалить/скрыть/переставить/проверить URL; предпросмотр для мобильного и ПК; состояние «не подтверждено» отдельно от «скрыто» и «опубликовано». Упорядочивание без влияния на песенные назначения.

**Никакой автопубликации.** Черновик → валидация/предпросмотр → «Сохранить черновик» → отдельное «Опубликовать», с защитой конфликтов RUN-108 и журналом. Не обещать автоматическую проверку владения: галочка — лишь ручное подтверждение администратора, а не галочка верификации платформы.

Возможные сервисы: Spotify, YouTube, YouTube Music, Apple Music, Instagram, TikTok, Facebook, Telegram, SoundCloud, Bandcamp, VK, VK Music, Яндекс Музыка, Deezer, TIDAL, официальный сайт. Платформы показывать только при наличии валидного публичного профиля.

## Данные: не плодить дубли

Стабильный `artistId` — ключ привязки к существующему артисту. `artists.cards` остаются 12 витринными карточками **главной страницы**, а не каталогом всех артистов. Для масштабирования — отдельные версионированные документы профилей **только после аудита текущих Firestore Rules** (например, административные drafts + отдельно опубликованные public snapshots, принципиально без публичного доступа к черновикам); или иной совместимый формат с теми же свойствами.

Пример поля ссылки (это проект схемы, а не deployed API):

```json
{
  "artistId": "dj-velar",
  "platform": "spotify",
  "url": "https://open.spotify.com/artist/1PNzGsDcFVuOMBN7Gw12tw",
  "category": "listen",
  "visible": true,
  "confirmedByAdmin": true,
  "sortOrder": 1,
  "primary": true
}
```

- Белый список безопасных HTTPS-доменов/пути конкретного провайдера; без `javascript:`, произвольных HTML/iframe, open redirects и дубликатов.
- В JSON-LD `sameAs` попадут **только** опубликованные, видимые и подтверждённые именно профильные URL (не страницы отдельных песен, не трековые URL, не URL c UTM).
- Отображать внешние ссылки и профиль в доступном текстовом HTML без обязательного выполнения JS и доступа поискового робота к Firebase. **Предпочесть статическую генерацию / prerender публичных артистских страниц из проверенного published-снимка.** Не публиковать приватный каталог/lyrics/Drive или секреты.
- Не изменять `vmm_links`, музыкальный каталог, сами песни и схемы прав доступа без независимого отдельного миграционного плана.

## SEO: важнее самих значков

Каждый артист должен иметь полноценный `200 OK` URL с уникальными `title`, `meta description`, `canonical`, `og:title`, `og:description`, `og:image`, фото/биографией, настоящими HTML-ссылками и внутренней ссылкой из списка артистов. Отдельно проверить `robots.txt`, sitemap.xml, noindex, GitHub Pages маршрутизацию и Google Search Console; не создавать дублей URL через hash-маршруты.

JSON-LD — `ProfilePage` + `mainEntity` типа `MusicGroup` (Schema.org включает сольных музыкантов) либо подходящего `Person`/Organization в зависимости от артиста; `name`, `url`, `sameAs`, фото/описание по доступности. Музыкальные релизы позднее могут ссылаться на артиста через стабильный `@id` и `MusicRecording.byArtist`. **Разметка не гарантирует rich result/knowledge panel/позиции.** Не выдумывать «verified» для социального аккаунта и не показывать непроверенные числа подписчиков.

Google документация: https://developers.google.com/search/docs/appearance/structured-data/profile-page ; https://developers.google.com/search/docs/appearance/structured-data/organization ; https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics ; https://schema.org/MusicGroup .

## Операционная выгода

- Один URL артиста для био в Instagram/TikTok/YouTube и для обмена; можно добавлять площадки без смены этого URL.
- В VELARDREAM можно переключать основную CTA на актуальный релиз или видео, не нарушая постоянный адрес и индексируемость.
- Аналитика в будущем — только минимальные агрегированные собственные клики по площадкам с уважением к согласию/приватности; без скрытого слежения, fingerprinting и ненужных внешних SDK. Не делать невозможные обещания об отслеживании подписок на сторонних сервисах.
- Разделы FI/EN/RU, редактор текстов, доступные кнопки, Safari12, слабая сеть, отсутствие данных в любой площадке.

## Приёмка перед включением

1. Ссылка относится к правильному артисту, правильной площадке, прямая, HTTPS, без дубля; проверена владельцем.
2. Черновик не виден гостям / SEO; публикация меняет только published; восстановление после ошибки не теряет старые данные.
3. Mobile Safari12/iPhone/PWA: тексты не обрезаются, кнопки доступны, новые вкладки и возврат на сайт работают.
4. Инспекция готового URL: HTTP 200, страница из исходного HTML, один canonical, noindex отсутствует **только после разрешения открытия**, sitemap содержит страницу; robots не блокирует.
5. Тесты: неверный провайдер, подмена домена, профиль vs трек, битая ссылка, многократные нажатия, скрытие, удаление, недоступность сети, конфликт черновика, смена языка, 13-й артист (не ограничивать общий каталог лимитом 12 витринных карточек).

## Следующий этап

## Уточнение владельца 13.11.2026 — ЕДИНАЯ АДМИНКА, БЕЗ ЛОГИНОВ АРТИСТОВ

**Решение владельца:** «Сайт — не социальная сеть; я сам размещаю материалы». Поэтому:
- **Запрещено проектировать вторую админ-панель, персональные кабинеты артистов, отдельный вход, регистрацию, роли редакторов или механизм разрешения индивидуального редактирования** в рамках этой функции. Даже «отключённую пока» систему делегирования не добавлять: это избыточная архитектура.
- Все поля социальных сетей, биографии, изображений, клипов и списка альбомов редактируются исключительно владельцем в **уже существующей Studio → Главная страница → Артисты → карточка артиста**, без дополнительного вложенного «Админ-меню». Внутри текущего редактора можно сделать аккуратные раскрывающиеся секции «Основные сведения», «Биография», «Социальные сети», «Музыка», а также необязательную кнопку **«Посмотреть публичную страницу»**, которая НЕ является админкой.
- Публичная отдельная страница артиста — только для посетителей: фото, подробная биография, музыка, видеоклипы, альбомы, официальные социальные ссылки; **никаких кнопок изменения и входа**. Постоянные URL и SEO-поля заполняются/генерируются через существующую Studio.
- Изображённая в ранее переданном прототипе «админка» — **макет существующей Studio**, а не предложение отдельного кабинета артистов. Это уточнение имеет приоритет над неоднозначными формулировками прототипа.
- Лимит `artists.cards` = 12 относится к карточкам **главной страницы**, а не к будущему отдельному каталогу артистов. Реализацию отдельного каталога требуется спроектировать совместимо и без лишних копий данных.
- Делегирование управления артистам *не входит* в текущую работу. Если когда-либо понадобится, отдельное новое решение только по явному запросу владельца.
- **Статус:** уточнена спецификация; реальный сайт, учётные записи, Firestore, правила, SEO-индексация не менялись.

## RUN-115 — фактическая реализация 13.11.2026 (состояние перед merge)

**Важное различие план/реальность.** Изначальная спецификация выше описывает идеальную отдельную статически подготовленную страницу на каждого артиста. В RUN-115 внедрён **общий публичный шаблон** `/artist.html?id=<artistId>` с чтением опубликованного `vmm_public_pages/landing`. У legacy-карточек без artistId есть `?name=`; при неоднозначных одинаковых именах профиль не угадывается. Такой подход сразу работает для каждой опубликованной карточки без новых документов Firebase, прав доступа и отдельной учётной записи.

В `landing-public.js` на карточке добавлена кнопка «Подробнее об артисте», внешний музыкальный линк сохранён. В существующем `studio/landing-editor.js` у артиста раскрывается блок «Персональная страница — биография и социальные сети»: длинная биография (до 5000 знаков), до 12 официальных профильных HTTPS-ссылок, видимость каждой, удаление/добавление и ссылка на **опубликованную** версию. Существующие поля, фото, лучшие песни и раздельное сохранение черновика и публикация не изменены. `landing-schema.js` добавляет проверку ссылок по платформам и сохраняет старые карточки, нормализуя новые поля в пустые. Публичный шаблон выводит биографию, фото, подтверждённые публикацией социальные ссылки, лучшие песни, альбомы при точном совпадении публичного имени, функцию «Поделиться» и возврат на главную. Публичный код читает только `vmm_public_pages/landing` и разрешённый локальный snapshot, без приватных данных.

**SEO-ограничение:** сейчас и главная, и шаблон артиста имеют `noindex,nofollow,noarchive`. Динамически выставляемые title, canonical и JSON-LD важны для будущей SEO-подготовки, но **не равнозначны статическому HTML** для роботов и предпросмотра социальных сетей. Нельзя обещать индексацию этих параметризованных страниц. Отдельный будущий этап: генерация статических страниц или серверный prerender из публичного published snapshot, уникальные социальные карточки, sitemap/robots и согласованное снятие noindex после проверки безопасности. Этого сейчас не делали.

**Участки:** `artist.html`, `artist-detail.js`, `artist-detail.css`, `landing-schema.js`, `landing-public.js`, `studio/landing-editor.js`, версии `index.html`/`studio/index.html`/`sw.js`, тесты. Без новых аккаунтов, Firestore Rules и пользовательских записей.
