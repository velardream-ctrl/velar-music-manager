# Будущий шаблон сайта: копируем код и функции, а не чужие данные

**Статус:** архитектурный план (не готовый клонируемый продукт). Цель — превратить VELARDREAM Studio в повторно используемую основу для музыкальных, учебных и других персональных кабинетов **без регрессий**.

## Принцип
Отделить **платформу** (логика, интерфейс, тесты) от **конкретного проекта** (бренд, коллекции, пользователи, песни, Google Drive, Firebase, разрешения). Новая копия получает собственные секреты, домен, Firebase-проект, Drive-папку, администраторов и пустую базу. Копирование исходного кода **никогда автоматически не копирует** приватные песни и контакты.

## Предлагаемые независимые модули
| Модуль | Что должен сохранять |
| --- | --- |
| Core / оболочка | экран входа, обзор, навигация и восстановление вкладки, темы/локализация, mobile-safe UI |
| Access | Firebase Google Auth, серверная проверка роли, разграничение пользователей/организаций |
| Catalog | выбор песен, фильтры, UPC/каталожная строка, связь с текстами/медиа |
| Lyrics | версии текста, неизменные поля идентичности, A4/PDF, крупное чтение, share TXT |
| Media | безопасная загрузка, лимиты/типы файла, транслитерация, проигрыватель, download, корзина/restore |
| Offline | IndexedDB по пользователю, выборочная синхронизация, проверка вместимости, статический SW |
| Audit / recovery | история CRUD, диагностика без личных данных, резервирование/восстановление, миграции |
| Integrations | адаптеры Google Drive / других провайдеров, конфигурация без токенов в репозитории |

## Конфигурация экземпляра
В отдельном конфигурационном файле и интерфейсе установки задавать: имя сайта и бренд, логотип/цвета, поддерживаемые языки, основной путь, набор модулей, роли, Firebase project ID/auth domain, коллекции и правила, Drive folder ID, MIME-типы/лимиты, список доступных страниц. Пароли, private keys и токены — **не в публичной конфигурации**. Значения пользователей и содержимое базы — не параметры темы.

## Как выпускать копию
1. Зафиксировать базовый релиз шаблона/tag с зелёными тестами (ещё не сделано).
2. Создать отдельный репозиторий из Template Repository; не копировать приватные данные/бэкапы.
3. Создать независимые backend, storage, OAuth и безопасные правила; выполнить проверки доступа до импорта контента.
4. Установить branding/config и включить нужные модули; запустить тесты совместимости.
5. При необходимости импортировать **только с явного согласия владельца** через валидируемую схему и резервную копию.
6. Протестировать мобильную навигацию, офлайн, загрузку/корзину, тексты/A4 и авторизацию на каждом новом сайте.
7. Вести собственные RUN/PR/CHANGELOG экземпляра; обновления шаблона переносить как контролируемые миграции, а не копированием файлов поверх данных.

## Порядок реализации, без спешки
- Этап A: стабилизировать VELARDREAM и закрыть RUN-051, ручные регрессионные проверки iPhone/Drive.
- Этап B: документировать контракт данных и модулей, вынести брендинг/настройки в конфигурацию.
- Этап C: выделить ядро, интерфейсы интеграций и миграции, не меняя поведение исходного сайта.
- Этап D: создать второй **пустой** демонстрационный сайт, прогнать тесты эквивалентности.
- Этап E: оформить GitHub Template Repo, каталог модулей, начальный setup wizard и стратегию обновлений.

## Критерии «шаблон готов»
- Две независимые установки без общего UID/Drive folder и без утечки данных.
- Сохранены все проверенные пользовательские функции VELARDREAM.
- Развёртывание не требует вручную править десятки исходников.
- Набор автоматических тестов + ручной iOS чек-лист зелёный для каждой установки.
- Версионирование, совместимые миграции и rollback; резервные копии до изменения схем.
- Никто не получает права администратора только потому, что видит GitHub Pages или знает URL.

**Пока не переносить на платный хостинг и не размножать текущую реализацию автоматически:** сначала снять регрессии и закрепить контракт данных.
